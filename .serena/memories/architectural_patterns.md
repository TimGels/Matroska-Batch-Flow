# Architectural Patterns

## Two-Stage Track Configuration Architecture

The application uses a **two-stage architecture** for track configuration that cleanly separates mechanical data collection from business logic presentation:

### Stage 1: Mechanical Per-File Population
- **Responsibility**: `BatchTrackCountSynchronizer`
- **Purpose**: Copy exact scanned values from MediaInfo to per-file configurations
- **Key Principle**: No business logic - just direct data transformation
- Populates: `IBatchConfiguration.FileConfigurations[path]` for each file

### Stage 2: Smart Global UI Population  
- **Responsibility**: `IFileProcessingRule` implementations
- **Purpose**: Analyze per-file data and determine smart defaults for global UI
- **Key Principle**: Apply business logic to decide what users see
- Populates: `IBatchConfiguration` global collections (AudioTracks, VideoTracks, TextTracks)

### Benefits
1. **Separation of Concerns**: Data collection vs. business decisions
2. **No Duplication**: Scanned data copied once by synchronizer
3. **Easy Testing**: Test data transformation and business logic separately
4. **Maintainability**: Change data sources or UI logic independently

### Command Generation Pattern
Commands are generated by comparing:
- **Global configuration** (what user sees/edits in UI)
- **Per-file configuration** (actual scanned values from MediaInfo)
- Commands generated only when global differs from per-file

See [two-stage-architecture.md](two-stage-architecture.md) for complete documentation.

## Configuration Management

### Two-Tier Configuration Model
The application maintains two distinct levels of track configuration:

1. **Global Configuration** (`IBatchConfiguration`)
   - Single instance containing UI-visible collections
   - Properties: `AudioTracks`, `VideoTracks`, `TextTracks`
   - Purpose: What the user sees and edits in the UI
   - Scope: Batch-wide defaults

2. **Per-File Configuration** (`FileTrackConfiguration`)
   - Stored in `IBatchConfiguration.FileConfigurations` dictionary
   - Key: Absolute file path
   - Properties: `AudioTracks`, `VideoTracks`, `TextTracks` (same structure as global)
   - Purpose: Actual scanned values for each file
   - Scope: Individual file metadata

### Configuration Flow
```
Scan File → Synchronizer populates per-file config → 
Rules populate global config → UI displays global config → 
User edits global config → Command generator compares global vs per-file → 
Generate mkvpropedit commands for differences
```

## MVVM Architecture (Uno Platform)

### View-ViewModel Separation
- Views: XAML UI definitions
- ViewModels: Presentation logic and state management
- Models: Domain entities and business logic (Core project)

### ViewModel Patterns
- The processing footer and blocking-check review banner bind to `MainViewModel.Availability` (reason and relevant count). Apply Changes is enabled only when files and configured edits are present, no checks block processing, and no batch operation is running. The banner's Review action opens a fresh batch-wide `FileCheckVisit`; it is hidden while viewing Validation or running a batch operation. The view resolves English fallback and translated strings from `Resources.resw` for the banner, button labels and automation help. Test availability by reason and count, not by display text.
- Validation and Input badges use `ValidationText` bindings for dynamic text and `x:Uid` for static labels. File topics, format issues, raw tags, missing slots and visit state stay independent of the resource language. Unstructured diagnostics and scanned identifiers are displayed verbatim.
- Every UI phrase is one complete `.resw` string. Code inserts only numbers, file names, scanned values or complete phrases separated by punctuation, never a translated word into a sentence. Phrases that name a track type use one key per type (`<Key>Audio` / `<Key>Video` / `<Key>Subtitle`, via `ValidationText.TrackKey`); a word used in different contexts (e.g. a heading for several checks and a label for one) gets a separate key per context.
- `TrackViewModelBase`: Base class for track-specific ViewModels
- Method: `UpdateBatchConfigTrackProperty` - synchronizes global and per-file configurations when user edits UI
- Pattern: ViewModels update both global (for UI) and per-file (for command generation) simultaneously

## Validation System

### Rolling Reference Strategy (`RollingReferenceComparer`)
Consistency rules that compare track properties across files use the **rolling reference strategy** via the internal `RollingReferenceComparer` static class in `Core/Services/FileValidation/`.

**Problem it solves**: Files in a batch may have different track counts (e.g., one file has 2 audio tracks, another has 3). A naive first-file-as-reference approach would skip positions that don't exist in the reference file, missing real inconsistencies.

**How it works**:
1. Rules build a **matrix** of track property values: rows = files, columns = track positions
2. For each track position, the **first file that has that position** becomes the rolling reference
3. All subsequent files with that position are compared against that reference
4. Files lacking a given track position are skipped for that index (no false positives)

**Rules that use this pattern** (all follow the same build-matrix → call-comparer structure):
- `DefaultFlagConsistencyRule` — validates `DefaultFlag` consistency across track positions
- `ForcedFlagConsistencyRule` — validates `ForcedFlag` consistency across track positions
- `LanguageConsistencyRule` — validates language tag consistency across track positions

**Adding a new property-comparison rule**:
1. Build a `List<List<T>>` matrix using a private `Build*Matrix` helper
2. Call `RollingReferenceComparer.Compare(matrix, files, trackType, severity, propertyName, checkKind)`
3. The comparer yields `FileValidationResult` for every mismatch found

**Validation rule interface**: All rules implement `IFileValidationRule` and are registered in DI. No explicit orchestration needed — `FileValidationEngine` discovers and runs them all.

### Contextual File Checks (ui-patterns, validation)

- `FileValidationResult` preserves its diagnostic message and severity, with a `ValidationCheckKind` and structured `ValidationComparison` snapshots for presentation. Do not parse messages to identify issues.
- Property comparisons share one snapshot per differing track position across result instances, including matching files but excluding files without that position. Run FileFormatValidationRule as a separate first stage. Unsupported files block in every mode but are excluded from all later comparisons; track-count evidence includes zero counts for supported files.
- `FileCheckSummary` groups findings by kind, severity, track type, and one-based position. The dedicated `ValidationPage` selects one topic and displays its impact, value counts and per-file comparisons; neither the reference nor the majority is described as correct. A compact selector replaces the side list on narrow windows.
- `InputViewModel` replaces its compact toolbar summary on validation events and updates existing `ScannedFileViewModel` indicators without rebuilding the file list or changing selection. Do not put expandable findings above the Input file list.
- `MainViewModel` exposes processing availability and a primary review action for blockers. The Validation tab sits next to Input. Opened from the navigation bar, it keeps its current FileCheckVisit like the other cached tabs; the review banner and Input toolbar pass a fresh batch-wide visit and per-file counts a file-scoped one. A file-scoped visit shows its value above the full comparison. Expandable rows show filenames by raw value; absent slots have their own contextual row and do not change the comparison participants. After revalidation, restore the topic and expanded value keys against live results, not saved file lists. TrackCheckInspection opens a batch-wide editor at the check's position; there is no Back navigation. Use the Input tab to return to the cached file list. Navigating away does not dismiss findings.
- Findings describe scanned metadata, not pending output edits. The UI must not claim a finding is fixed merely because the user configured a change.

## Processing Pipeline

### File Processing Sequence
1. User adds files to batch
2. MediaInfo scans each file
3. `BatchTrackCountSynchronizer` creates per-file configurations (Stage 1)
4. `FileProcessingEngine` applies all `IFileProcessingRule` implementations (Stage 2)
5. Global UI collections populated with smart defaults
6. User can view/edit global configuration
7. Command generator compares global vs per-file to produce mkvpropedit commands

### Extensibility
- New rules: Implement `IFileProcessingRule` interface
- Automatic discovery: All rules registered in DI container
- Sequential execution: Rules applied in registration order

## Batch Processing Progress and Cancellation

### Progress plumbing
`ProcessRunner` (`onOutputLine` callback, background thread) → `MkvPropeditOutputParser.TryParseProgress` (`label: N%`) → `IProgress<int>` passed to `IMkvToolExecutor.ExecuteAsync` → per-file `Progress<int>` created by `FileProcessingOrchestrator` → `FileProcessingReport.Progress` (only while the file is `Running`) → `BatchExecutionReport.CurrentFile` / `Completed` / `OverallProgress`.
- mkvpropedit only reports progress for operations that read the whole file (e.g. `--add-track-statistics-tags`)
- `MkvPropeditExecutor` adds `--ui-language en` on Windows only and strips progress lines from stored output
- `Completed` and `OverallProgress` exclude `Canceled` files, so a canceled batch stays below 100%
- `FileProcessingOrchestrator` must not use `ConfigureAwait(false)`: `Progress<T>` and status changes rely on the captured UI context

### Cancellation
A running mkvpropedit is never stopped. It edits the file in place, and its progress lines reach the app through a pipe and a reader thread, so they lag behind the process: a percentage below 100% does not prove that writing has not started, and killing it could corrupt the file. `MkvPropeditExecutor` therefore passes `CancellationToken.None` to `ProcessRunner` and only checks the caller's token before starting. Cancel lets the current file finish (it is reported with its real result) and the orchestrator marks the remaining files `Canceled` before start. Do not reintroduce killing the process unless mkvpropedit gains a cooperative safe-stop mechanism.

### UI
- `MainViewModel` subscribes to the active `BatchExecutionReport` while processing and builds an `OperationOverlayState` (`ProcessingOverlay`); `MainPage` shows the shared `OperationOverlay` over the whole window, with Cancel bound to `CancelProcessingCommand`. `IsInteractionEnabled` disables the `NavigationView` and command bar, because arguments are built per file from the live configuration
- `IBatchOperationGate` serializes batch processing with pipeline runs (import, removal, revalidation), which change files and track intents. `PipelineRunner` waits for the gate; `MainViewModel.ProcessBatchAsync` uses `TryEnter` and refuses to start while an import is running (it does not wait, so it never processes changes the user has not reviewed), then checks files, blocking validation errors and arguments while holding the gate. `CanProcessBatch` (Apply Changes and Show Arguments) is false while the gate is busy
- The result dialog is sent after the overlay is hidden; a run with canceled files shows "Batch Cancelled"

## Batch Results and History

- `BatchHistoryService` serializes writes across instances with a persistent, empty `.lock` sidecar (`Utilities/FileLock`, also used by `WritableJsonSettings`). Under that lock, reload and merge `BatchHistory.json` before saving; preserve unreadable, unsupported or incomplete history (required IDs, timestamps, paths and statuses; valid enum values; no duplicate IDs). If the persisted settings limit cannot be read, save and show all runs without trimming; reject a null `UserSettings.BatchHistory` section. A failed add shows the history it just read (falling back to the visible runs only if reading failed), so runs cleared by another instance do not reappear. Clear failures keep the visible runs.
- A successful clear commits a fresh non-empty `ClearId` in v3 history; retain v1 marker-free writes and v2's required, non-default `ClearedAt` on ordinary saves. Treat the marker as an identity, not a time. Open the history snapshot with delete sharing before an add waits for either lock and keep its marker with the pending result. An intervening clear invalidates it. If the initial marker cannot be read and the next readable history has an unfamiliar clear, show that run only in this session, without consuming persisted retention. A later clear removes it. `HasUnsavedRuns` warns for these rows as well as retryable failed writes; closing the app loses both.
- `SettingsViewModel` refreshes the history limit from disk when navigated to, but only when no confirmation is pending and `_historyLimitLock` is free. Recheck both conditions after the asynchronous read and do not treat a refresh as a user edit. `BatchHistoryLimitSaveFailed` also blocks refresh, so clear it whenever the edit is abandoned: Cancel, or a value equal to the limit in effect. On navigation, discard a failed edit that does not wait for confirmation and show the limit in effect; keep a failed confirmation pending.
- Loading publishes saved runs even when the limit cannot be read, and only a successful load is cached, so the Results page retries it. Confirming a lower limit writes the trimmed history before saving the limit: a failed history write changes nothing, and a failed limit save leaves only the confirmed runs removed with the previous limit in effect. Never save a lower limit before its trimmed history, because later saves would remove unconfirmed runs.
- `WritableJsonSettings.UpdateAsync` diffs the cached settings before and after the delegate and writes only the changed values over the saved file, so another instance's settings survive. Failed writes retain only delegate changes for retry; unrelated cache refreshes are excluded, and a later delegate can replace a pending value. If a failed change must not be retried, pass a restore delegate to `UpdateAsync`; it restores the cache and removes those pending values while still holding the lock, so a queued update cannot persist the rejected value. Change settings only inside the delegate.
- Retention edits are serialized in `SettingsViewModel`. The history service checks the confirmed removal count against disk while it holds the storage lock; an outdated confirmation never removes more results than the user saw. Cancel is unavailable while Confirm is saving. If saving the limit fails after trimming, `BatchHistoryLimitSaveException.HistoryTrimmed` tells the view model whether the trim committed; close the prompt only on that signal, never by comparing the possibly stale local run count with the limit.
- Keep pending and running status in finished snapshots: the batch was interrupted, not canceled. A pending file was not started; an interrupted running file may have changed. Skipped only means no requested changes applied. Copying command diagnostics does not produce a shell-ready command.
- Each `BatchRunSummary` retains the `FileResultItem` instances for that run. Use the row's observable `IsExpanded` with a two-way binding so repeater recycling does not mix up file expansion state.
- Show all seven summary tiles for a selected batch, including zero counts. Each tile uses the same localized description for its hover tooltip and accessibility help. Offer file filters only for outcomes present in that batch.
- `ITaskbarProgressService` mirrors `OverallProgress` on the taskbar button (paused while cancelling) via `ITaskbarList3` on WinAppSDK and on Skia Desktop running on Windows
